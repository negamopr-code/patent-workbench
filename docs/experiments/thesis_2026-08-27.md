# Does a NotebookLM screen earn its place in front of an Opus reading funnel?

**Closing thesis of the patent-workbench screen-viability study · 2026-08-27 · hypothesis-driver agent**
Supersedes `thesis_2026-08-25.md`. Register: `docs/experiments/hypotheses.md` (H1–H16, all terminal).
Written under a hard analysis-only constraint: 0 opus reads, 0 NotebookLM jobs launched for this document.

---

## 1. Abstract

**Question.** A five-tab patent-prior-art workbench runs a three-stage funnel: a NotebookLM
"screen" that graduates or rejects each fetched document, an optional NotebookLM follow-up
("stage-2") on survivors, and a Claude-Opus-5 blind deep read that produces the only
verdict anyone trusts. Does the screen earn the NotebookLM quota and the four days of
wall-clock it costs, or should the corpus go straight to Opus?

**Method.** Blind, pre-registered hypotheses (H1–H16), each closed by the cheapest decisive
test available; ~4 156 Opus verdicts on t10–t14, exhaustive reads of two complete reject
pools, an independent full-text NotebookLM interrogation of 118 previously-unseen document
tails, a controlled A/B on question wording, and cadence measurements over 161 screen rounds.

**Headline answer.** The screen is a **topicality filter**, not a feature matcher. Inside
the current (v2) screen scope it kept **31 of the 34 champions it actually judged (91.2 %)**
and dropped **zero** on the two tabs whose reject pools are exhaustively read — but it lost
**10 more champions before judging them at all**, because those documents were never indexed
in NotebookLM. End-to-end v2 champion recall is therefore **31/44 = 70.5 %**, and the screen
removes only **39 % of the corpus** from the read queue (10 % on t12, 14 % on t13). Its
positive signal is carried **entirely by weight-1…3 category boilerplate**; every weight-4
and weight-5 feature contributes exactly zero discrimination. And every negative the whole
pipeline has ever produced is conditional on benchmark vocabulary: with the document and
feature list held constant, rewording one feature flipped **NO/NO/NO → YES/YES/YES** on the
two highest-weight features of a checklist.

## 2. Background

### 2.1 The pipeline

| stage | instrument | unit of work | what it produces |
|---|---|---|---|
| fetch | app | document | `documents` row with claims + description |
| **screen** | NotebookLM, roster ≈ 39 docs/round, one notebook per tab | round | `nlm_screen_state` ∈ {`graduate`, `rejected`, `add_failed`} + a graduation ordinal |
| **stage-2 follow-up** | NotebookLM, `scripts/nlm_followup.py`, ≤10 docs per dedicated notebook | doc | per-feature YES/PARTIAL/NO with citations (F3b control) |
| **deep read** | `claude-opus-5` via `POST /api/tabs/{t}/deep-compare`, blind (`deep_map` sees benchmark + features + document text only) | doc | `score` 0–8 + `feature_scores` JSON |

"Champion" = Opus score ≥ 4.0. "Borderline" = ≥ 3.0. Tabs are bound to fixed NotebookLM
accounts, permanently: t10 = drawnformula, t11/t13 = default, t12/t14 = work2.

### 2.2 The truncation NO-GO and the v1/v2 epochs

Until 2026-08-23 the screen staged each document **clipped at 120 000 bytes**, so the tail of
every long patent was invisible to NotebookLM. On 2026-08-23 19:00 UTC the user declared a
**truncation NO-GO**: everything is staged in full, split into multi-part sources. That
timestamp (epoch `1787511600`) partitions all screen evidence:

* **v1** — `nlm_screened_at < 1787511600`: truncated staging. Historical, not evidence about the current pipeline.
* **v2** — `nlm_screened_at ≥ 1787511600`: full multi-part staging. **2 556 documents across five tabs.** All five v2 screens finished (`step=done`) overnight 08-26/08-27.

This distinction is load-bearing: the auditors' headline "42 Opus ≥4 documents were REJECTED
by a finished screen" is **39 v1 rejections and 3 v2 rejections**.

### 2.3 Ground-truth canaries

Each tab carries registered controls (documents known to be relevant). Two problems were
measured earlier in the study and matter here: (a) 8 of t10's 12 GT controls turned out to be
**stale** — scored under a feature set that was later rewritten (H8), leaving 4 valid ones;
(b) no tab has a *verbatim* canary, so corpus-wide negative claims stay scoped (audit_recall R3).

## 3. Method

**Blindness.** Every Opus verdict in this study came from `deep-compare` with
`reading_model = model = claude-opus-5`, which shows the model the benchmark, the feature
list and the document text — never the screen's decision, never the ordinal, never another
model's score. Screen and reader cannot contaminate each other.

**Sampling.** Read batches were seeded manifests written to `/data/audits/*.json` before
launch, each naming the hypothesis it served and the expected information gain, and logged
to `docs/experiments/read_ledger.jsonl`. Two reject pools were driven to **exhaustion**
(t12 33/33, t13 66/66) rather than sampled, because a complete pool converts a rate estimate
into a count.

**Thresholds.** Champion ≥ 4.0, borderline ≥ 3.0, unchanged all study. Ordinal buckets
1–3 / 4–10 / 11+ fixed in cycle 1.

**Hypotheses and the test each got.**

| id | claim | cheapest decisive test, and why it was cheapest |
|---|---|---|
| H1 | miss class = old non-CJK docs | profile-matched reject reads (30) + **free** re-use of today's 118-doc restage, a pool that *is* the profile |
| H2 | over-clip subsets hold no unread champions | exhaustive read of one small scope (t12: 319 docs) instead of sampling five |
| H3 | stage-2 ≈ Opus | calibration against two documents whose Opus answer was already known (no new information needed, so any disagreement is instrument error) |
| H4 | judged-miss rate generalises across accounts | drive two reject pools to exhaustion; sampling could never prove "zero" |
| H5 | rank carries no ordering | zero-cost join of the ledger ordinal against verdicts already in the DB |
| H6 | screen keys on boilerplate | **the study's luckiest test**: today's restage independently interrogated 118 documents on all 22 features, giving a per-feature graduate-vs-reject contrast for free |
| H7 | champions are lost to `add_failed`, not judgment | read the entire `add_failed` pool on four tabs (313 reads) — the pool is small and the answer is a count |
| H8 | stale verdicts unreliable | re-read the 3.0 band blind (114) and compare to a snapshot |
| H9 | t10's `add_failed` champions are stale | 6 targeted re-reads |
| H10 | non-zero judged-miss rate | detector query over the DB (0 reads) + the exhausted pools |
| H11 | v2 scope excludes champions and isn't the stated rule | pure SQL on document sizes (0 reads, 0 quota) |
| H12 | global bridge lock serialises screens | round-cadence statistics from `nlm_screened_at` (0 reads) — the app logs did not survive the Docker restarts |
| H13 | rounds graduate a fixed number | round clustering by 5-s buckets (0 reads) |
| H14 | rejection rate is tab-dependent | counts at screen completion (0 reads) |
| H15 | t10's screen loosened after a restart | split the graduate pool at the restart timestamp and compare champion yield (0 reads) |
| H16 | recall floor is set by benchmark vocabulary | **controlled A/B**: same document, same features, one wording changed — the only design that isolates wording from content |

## 7. Conclusions on pipeline viability

**(a) What the pipeline reliably finds, and what it misses.**
It reliably finds **on-topic documents**. Inside the v2 scope the screen kept 31 of the 34
champions it judged (91.2 %), it kept 4/4 valid GT canaries on t10, and on the two tabs whose
reject pools were read to exhaustion it missed nothing (0/99). Its head is genuinely informative:
graduation ordinal 1–3 carries a 38.5 % champion rate against 2.1 % at ordinal 11+ (18×).
It misses three things. First, **documents it never saw**: 119 `add_failed` (F3c-ns) hold 10
of the 44 v2 champions — the largest single loss in the funnel, and a plumbing bug, not a
judgment. Second, **documents whose vocabulary differs from the benchmark's** (H16): a narrow
genus term in one feature produced three false NOs on the two highest-weight features of a
checklist, and that mechanism sits upstream of the screen, the sweep and the follow-up alike.
Third, **whatever was decided under v1 and never retested**: 39 rejected champions, one of
them a registered 8.0 control. Judged misses proper are rare — 3 in 299 read v2 rejects (1.0 %).

**(b) Does the NLM screen earn its quota versus going straight to reads?**
**Barely on t10 and t14; no on t12 and t13; and not at all in its current configuration.**
The screen's only economic product is the reject pool, i.e. reads you don't have to buy. It
delivered 39 % of the corpus pooled — but 10 % on t12 and 14 % on t13, where 80 %+ of everything
graduates (H14). Against that saving stands: three NotebookLM accounts occupied for four days,
119 documents silently dropped (10 champions), a 1.0 % judged-miss rate, and a signal that is
**entirely topical** — the per-feature contrast shows the screen separating documents on
"is there a battery / is this a charging method", with *zero* contribution from any weight-4 or
weight-5 feature (H6). A cheap lexical or embedding filter can reproduce a topicality cut at no
quota cost. The honest formulation: **the screen is worth running only where its rejection rate
is high (t10 39 % graduation, t14 69 %), and only as a triage order — never as a clearance
instrument.** On t12/t13 it should be switched off in favour of reading everything.
Caveat on the auditor's blunter version of this ("no measurable lift on 4 of 5 tabs": graduate
vs reject hit rates t10 1.5/1.2 %, t11 16.4/15.3 %, t12 1.9/3.3 %, t13 2.5/1.0 %, t14 11.7/10.5 %):
that comparison is biased *against* the screen in one direction and *for* it in another — every
graduate is read (unbiased) while read rejects are lane-selected suspects (enriched). The
unconfounded measurement is §6.4's restage: **3.6× feature yield, p = 5e-5**. The screen does
discriminate. It just discriminates on topic, not on invention.

**(c) What the truncation/restage evidence changed.**
The truncation NO-GO (08-23) was expensive insurance, and today's restage says the insurance
was **not needed for recall on t14**: 118 previously-blind tails were re-staged in full and
interrogated, and **117 of them disclose no weight-4/5 feature at all**; zero champions were
recovered. The tails were long, but they were boilerplate. What the restage *did* deliver is
the best measurement in the whole study — the per-feature contrast that settles H6, and the
final nail in H1 (the "old non-CJK" pool is champion-free). It also shrank t14's blind pool
from 128 to 10 and produced a reusable evidence format (per-doc YES/PARTIAL/NO with citations,
persisted to `/data/audits/restage/`) that earlier follow-up runs threw away. Net: full staging

## 8. Limitations and admissibility

* **Pre-audit.** All three auditors ran 07:05–07:12 UTC today (head 09f61a9) and all three returned worst = **FAIL**. No `pipeline-integrity-supervisor` pass has gated the numbers in this document. Registered baselines are also stale: the approved scope texts still quote "recall 7/12" (t10) and "1/14" (t13) against measured 11/13 and 7/21, and S5 `add_failed` is 119 against a registered baseline of 13.
* **Unregistered baselines.** R2-batch-corridor is registered only for t10 (59) and t13 (119); t11 46, t12 61, t14 80 remain unregistered FAILs.
* **Tabs without controls.** t12 has no champion inside the v2 scope, so **t12's corpus recall is unmeasured**; its only registered control was rejected under v1 and never retested. No tab has a verbatim canary except t13, so corpus-wide negatives are scoped everywhere.
* **Selection bias in reject reads.** Only t12 and t13 have exhaustively-read v2 reject pools. t10 (169/767), t11 (21/72) and t14 (10/66) reject reads are lane-selected and enriched for suspects; their miss rates are upper bounds, not estimates.
* **Correlated instruments.** §6.4's graduate-vs-reject contrast uses NotebookLM to judge NotebookLM's own decisions. The two runs differ in staging (truncated vs full), notebook, roster size (39 vs 10) and question form (screen prompt vs per-feature checklist), but they share a model family; a genuinely independent adjudicator would be Opus, and only 5 of those 118 documents carry an Opus verdict.
* **Small n where it matters most.** H16 rests on one document and three features. H3's calibration is two documents. H10's judged misses are three documents.
* **Excluded data.** The restage chunk `t14_1787834464` (10 documents) is excluded from all feature statistics: its broad query failed with a transport error and its answers exhibit the label-collision artefact. `audit_staging` likewise does not credit those 10, so t14's blind pool is 10, not 0.
* **Token accounting is a proxy.** No bridge-reported usage exists; costs are `len(claims)+len(description)` at launch, or 25 k tokens/read where unmeasured.
* **Wall-clock confounds.** Six Docker/WSL restarts between 08-25 and 08-27 cut in-flight jobs and destroyed the app logs that would have settled H12 and H15 causally.
* **This cycle launched nothing.** Per the user's 16:10 directive: 0 Opus reads, 0 NotebookLM jobs. Three restage runners (t11, t13 on default; t14 on work2) were live throughout and were not touched; the NLM mirror sync was deliberately **not** run because it writes to a default-account notebook while a default-account job is running (A2 gate).
