# Thesis — Is the NotebookLM v2 screen a viable stage-1 filter for the patent workbench? (hypothesis-driver, 2026-08-24/25)

PRE-AUDIT: pipeline-integrity-supervisor + recall/ranking/staging auditors have not gated
these numbers (see §8).

## 1. Abstract
Question: does the NotebookLM v2 screen (39-doc rounds, full multi-part staging) miss
opus-grade champions, and if so, by judgement or by plumbing? Method: 423 blind
claude-opus-5 full-text reads across 9 jobs on tabs 10–14, organised as 10 hypotheses with
the cheapest decisive test per line; analytic checks on the app's own state files.
Answer: among docs that actually reached NotebookLM, the v2 screen has rejected 0 of 114
opus-read rejects at ≥4 and graduated all 4 valid t10 controls; the losses are upstream —
a deterministic 50-source cap overflow evicts 25–47 % of every round (`add_failed`),
value-neutrally, taking 5 of t10's 9 and 6 of t14's 17 champions. The t10 ground-truth set
was 8/12 stale; four controls plus five re-verified champions are the new canary set.

## 2. Background
Pipeline: (1) NLM screen — each round stages the benchmark + 39 candidates (+10 survivors)
in a rolling notebook and asks one ranked question; named docs "graduate", others are
"rejected"; (2) stage-2 per-feature citation follow-up on every graduate (F3b,
nlm-followup-verifier); (3) opus funnel — claude-opus-5 full-text reads with per-feature
YES/PARTIAL/NO and a 0–8 score (champion ≥4, borderline ≥3). Decisions: truncation NO-GO
(08-23) — every source is staged in ≤118 KB parts, no clipping; re-screen scope = the
1554 over-clip docs; GT canaries = t10's 12 registered opus-≥4 docs (08-21 calibration).
Failure classes: F3a batch-answer competition, F3b missing follow-up, F3c staging clip /
not-staged, F3e no post-sweep recall measurement, F4 rolling-notebook confound, F7 gates
rely on session discipline.

## 3. Method
Blind design: opus reads go only through `POST /api/tabs/{t}/deep-compare`
(`reading_model=claude-opus-5`, `skip_scored=false`, explicit `doc_ids`); the reader sees
benchmark + features + doc text, never the screen's verdict. One job per tab (lock file);
cap 60 reads per cycle; every job is registered with hypothesis + expected gain before
launch (read_ledger.jsonl). Sampling: pre-register manifests
opus_parallel_2026-08-24{.json,_wave2.json} (seeded per tab); cycle jobs use complete
pools (all unread docs of a state) rather than samples where the pool ≤ cap. Thresholds:
≥4 champion, ≥3 borderline; "v2-screened" = `nlm_screened_at ≥ 08-23 19:00`.

Hypotheses and the test each got (cheapest decisive):
- H1 old non-CJK miss class → read the 16 unread profile-matched t10 rejects (any ≥4 supports).
- H2 no unread champions in over-clip slices → read the unread graduates + rejects (0 ≥4 supports).
- H3 stage-2 ≈ opus → no reads; needs the verifier's per-doc verdicts (all 25 stage-2 docs already opus-read).
- H4 t14 miss rate on t11/t13 → no reads until the default account answers ~150 docs.
- H5 rank carries no ordering → ledger ordinals of the ≥3 graduates (no reads).
- H6 keys on boilerplate → feature split graduates vs judged rejects (no reads).
- H7 rejects' champions are staging failures → t12's 32 never-scored add_failed (cycle 1); t11 31 + t13 7 add_failed (cycle 2); analytic per-round cap-overflow prediction from the screen state files (cycle 2).
- H8 GT set stale → blind re-read of the 7 unverified controls + US20230337972 (user-approved, snapshot first).
- H9 t10 add_failed champions stale → blind re-read of the 6 (same job as H8).
- H10 v2 judged-miss rate → partition the recall audit's misses by screen epoch (no reads).

## 7. Conclusions on viability
The screen's judgement is not the bottleneck on the v2 re-screen: no opus champion that
reached NotebookLM has been rejected so far, and graduation carries the real controls at
the top of the roster. The screen is good for cheap stage-1 filtering of large over-clip
queues; it is not a ranking device (H5) and not yet usable for recall claims, because a
deterministic staging cap evicts a third to a half of every round before judgement.
Proposed (not implemented): cap-aware batch fill (shrink the roster until
Σparts+survivors+1 ≤ 50, carry overflow); re-queue add_failed and treat it as F3c "not
staged" in the gate matrix with its own denominator; full-timeout second-chance wait with
per-round loss logging; GT hygiene (re-read controls after feature updates, score
history, re-register the canary set); audits partition on screen state and epoch.

## 8. Limitations and admissibility
Outstanding gates: supervisor + staging/recall/ranking verdict files on the current head;
the recall lines here use re-verified, not yet REGISTERED, controls; t12 has no controls;
the three-way table covers 7 docs only (all v1-epoch); the registry now carries F3c-ns
(not-staged) baselines and R2-screen-roster39=39 (fc6e576) — v2 runs roster 39 on every
tab, outside the F3a corridor (≤12), so a v2 judged-miss class may still surface once
t11/t13 answer; account sharing is user-registered per fc6e576; t11/t13 have ≤1 v2 round; t10 has 97 unread add_failed docs (needs user
approval; expected 0–1 champions at the population rate, but the read part of that pool
was lane-selected); every verdict is a single opus-5 read (no repeat variance); token
numbers are a chars/4 proxy; 741 clipped-and-never-read docs and 1 025 pre-epoch
truncated verdicts on t11–t14 (auditors) are outside this thesis's scope.
